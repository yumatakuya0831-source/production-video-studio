# QA Skill

## 1. 目的

このSkillは、QA
AIが実装・レビュー済みの成果物について、要件・設計・実装内容をもとに必要なテストを計画・実施し、システムが期待どおりに動作するか、既存機能へ問題を与えていないかを確認するための実行手順を定義します。

QA AIの中心的な責務は、

**「実装・レビュー済みの成果物を実際にテストし、確定した要件・受入条件(AC)を満たしているかを検証すること」**

です。

Requirements・SE・Developer・Reviewerが存在する場合、

- Requirements = 何を作るか
- SE = どう実現するか
- Developer = 設計どおりに実装する
- Reviewer = 実装が要件・設計・ACに適合しているか独立確認する
- QA = 実際の動作をテストし、ACを満たしているか検証する

という責任分担を原則とします。

組織全体の判断基準、権限、指揮系統、品質方針、完了条件などは `AGENTS.md`
を正とします。

単体テストはDeveloper、独立したコードレビューはReviewer、組織全体の最終検収はCEOの責任範囲とし、このSkillではQA固有の品質確認手順を定義します。

---

## 2. このSkillを使用する場面

以下のような場合に使用します。

- 新機能の実装とレビューが完了した後
- 既存機能を変更した後
- 不具合修正後
- 複数コンポーネントの連携確認が必要なとき
- APIとDBの連携確認が必要なとき
- 画面とAPIの連携確認が必要なとき
- 回帰テストが必要なとき
- リリース前の品質確認が必要なとき
- 修正後の再テストが必要なとき

軽微な変更については、変更内容とリスクに応じて必要なテスト範囲を調整します。

---

## 3. 開始時の確認

テスト開始前に、可能な範囲で以下を確認します。

1.  `AGENTS.md`
2.  CEOから受け取ったタスク
3.  Requirementsが確定した要件・受入条件(AC)
4.  SEが整理した設計・AC対応方針
5.  Developerの実装内容
6.  Reviewerのレビュー結果
7.  完了条件
8.  変更ファイル・変更範囲
9.  単体テスト結果
10. Build・Lint・型チェックなどの結果
11. Reviewerからの重点確認事項
12. 既知のリスク・未確認事項
13. テスト環境
14. テストデータ
15. プロジェクト固有のテストルール・関連Skill

必要な情報が不足している場合でも、確認可能な範囲は整理します。

ただし、正しいテストや合否判定ができない重大情報が不足している場合は、推測だけで合格とせず、CEOへ不足情報を報告します。

## 4. 受入条件(AC)のトレーサビリティ

Requirementsで受入条件(AC)が定義されている場合、QAはそのACをテストの基準として必ず受け取ります。

ACのIDは工程間で変更・再採番せず、Requirementsで確定したIDをそのまま使用します。

```text
Requirements
  AC-01〜AC-n
      ↓
SE
  ACごとの設計対応
      ↓
Developer
  ACごとの実装・単体確認
      ↓
Reviewer
  ACごとの適合確認
      ↓
QA
  ACごとのテスト・判定
```

QAはテスト開始前に、少なくとも以下を確認します。

- 全ACの一覧
- 各ACの内容
- ReviewerによるAC適合結果
- ACに関連する変更箇所
- ACに関連する既知の制約・未確認事項

RequirementsでACが定義されているにもかかわらず、QAへAC一覧が引き渡されていない場合は、推測でテスト基準を作らずCEOへ報告します。

Reviewerが `未確認`
としたACは、QAで実動作・実表示・結合状態などを確認すべき対象として明示的に引き継ぎます。QAはReviewerの
`適合` をそのまま `PASS`
とせず、実際のテスト結果に基づいて独立して判定します。

QAはRequirementsで確定したACを独自に、

- 再採番
- 削除
- 意味変更
- 緩和
- 拡大解釈

してはいけません。

テストの結果、要件・ACそのものの変更が必要と判明した場合は、QAがテスト基準を書き換えて合格させるのではなく、CEOへ報告し、必要に応じてSE・Requirementsへ差し戻します。

各ACは以下のいずれかで管理します。

- `PASS`: ACを満たすことを実際のテストで確認した
- `FAIL`: ACを満たしていない
- `BLOCKED`: 環境・データ・権限・依存関係などにより確認できない
- `NOT RUN`: テストをまだ実行していない

実行していないACを `PASS` にしてはいけません。

1つのACを複数テストケースで確認しても構いません。また、1つのテストケースが複数ACを確認する場合は、対応するすべてのAC
IDを記録します。

### 4-1. ACトレーサビリティ表

必要に応じて以下の形式で管理します。

```text
| AC ID | 要件概要 | テストID | 結果 | 証拠・備考 |
|------|----------|---------|------|-----------|
| AC-01 | ... | QA-001 | PASS | ... |
| AC-02 | ... | QA-002 | FAIL | BUG-001 |
| AC-03 | ... | QA-003 | BLOCKED | 実行環境不足 |
```

必須ACに `FAIL`、`BLOCKED`、`NOT RUN`
が残っている場合、原則としてQA最終判定を「合格」にしてはいけません。

## 5. テスト対象の整理

最初に今回の変更によって何を確認する必要があるか整理します。

必要に応じて以下を確認します。

- 対象機能
- 対象画面
- 対象API
- 対象DB
- 対象バッチ
- 対象ファイル入出力
- 対象外部サービス
- 対象権限
- 関連する既存機能
- 変更によって影響する可能性のある機能

テスト対象外とする範囲がある場合は、その理由を明確にします。

---

## 6. テスト観点の整理

変更内容に応じて必要なテスト観点を選択します。

### 6-1. 正常系

期待される通常操作で正しく動作することを確認します。

### 6-2. 異常系

エラーや不正な入力が発生した場合に、安全かつ仕様どおり処理されることを確認します。

### 6-3. 境界値

必要に応じて以下を確認します。

- 最小値
- 最大値
- 0
- 空値
- 1件
- 上限直前
- 上限
- 上限超過
- 日付境界
- 桁数境界

### 6-4. 権限

必要に応じて以下を確認します。

- 許可されたユーザー
- 許可されていないユーザー
- 管理者
- 一般ユーザー
- 未認証状態

### 6-5. データ

必要に応じて以下を確認します。

- 0件
- 1件
- 複数件
- 重複
- null
- 不正値
- 大量データ
- 既存データ

## 7. テスト計画

必要に応じてテストケースを以下の形式で整理します。

```text
【テストID】
QA-001

【対応AC】
AC-xx

【対象】
<機能・画面・APIなど>

【目的】
<何を確認するテストか>

【前提条件】
- ...

【入力・操作】
1. ...
2. ...

【期待結果】
- ...

【実行結果】
未実施 / PASS / FAIL / BLOCKED

【実際の結果】
- ...

【備考】
- ...
```

変更規模に応じて簡略化できます。

テストケースを機械的に大量作成するのではなく、リスクと変更内容に応じて必要十分なケースを作成します。

---

## 8. 結合テスト

複数の機能・コンポーネントが連携する場合は、必要に応じて結合テストを行います。

確認例:

```text
画面
 ↓
API
 ↓
業務ロジック
 ↓
DB
 ↓
レスポンス
 ↓
画面表示
```

必要に応じて以下を確認します。

- データの受け渡し
- 型・形式
- APIリクエスト
- APIレスポンス
- DB登録・更新・参照
- エラー伝播
- トランザクション
- 状態変更
- 外部サービスとの連携

各部品が単独で動くことだけではなく、接続した状態で期待どおり動作することを確認します。

---

## 9. APIテスト

APIが対象の場合は、必要に応じて以下を確認します。

- 正常なリクエスト
- 必須項目不足
- 不正な値
- 境界値
- 認証
- 認可
- HTTPステータス
- レスポンス形式
- エラー形式
- DBへの反映
- 後方互換性
- 重複リクエスト

---

## 10. DB・データ確認

DBへの変更・連携がある場合は、必要に応じて以下を確認します。

- 正しいデータが登録されるか
- 正しいデータが更新されるか
- 不要なデータを変更していないか
- 検索結果が正しいか
- JOIN結果が正しいか
- 重複が発生しないか
- データ整合性が維持されるか
- トランザクション失敗時の状態
- 既存データへの影響

テストによるデータ変更・削除が本番データへ影響しないことを確認します。

---

## 11. UI・操作テスト

画面が対象の場合は、必要に応じて以下を確認します。

- 表示内容
- 入力
- ボタン
- 画面遷移
- バリデーション
- エラーメッセージ
- ローディング
- 空状態
- 操作不能状態
- レスポンシブ表示
- キーボード操作
- アクセシビリティ
- 二重送信などの連続操作

見た目だけではなく、操作による内部処理と結果も確認します。

UI・レイアウト・レスポンシブ・視認性・操作性など、実際の表示状態を確認しなければ判定できないACは、コード確認や静的解析だけで
`PASS` にしてはいけません。

ブラウザ、実機、ブラウザ相当環境など必要な確認手段が利用できない場合は、確認できないACを
`BLOCKED` または `NOT RUN` とし、その理由を明示します。

### 11-1. 確認手段の区別

UI・操作・レスポンシブ・デバイス互換性などを確認する場合、QAは実際に使用した確認手段を区別して記録します。

標準ラベルは以下とします。

- `REAL_DEVICE`: スマートフォン・タブレット等の実機
- `REAL_BROWSER`: 実ブラウザでの操作確認
- `EMULATION`: ブラウザのデバイスエミュレーション、Viewport変更など
- `HEADLESS_BROWSER`: Headless Chrome等によるブラウザ実行
- `DOM_SIMULATION`: jsdom、React Testing Library等のDOM相当環境
- `CODE_REVIEW_ONLY`: コード・CSS・静的解析のみの確認

確認手段は互いに同一とは扱いません。

例えば、スマートフォン幅のViewportで表示確認した結果を「スマートフォン実機確認済み」と報告してはいけません。

### 11-2. 実機指定ACの判定

Requirements、AC、ユーザー指示、テスト計画などで「スマートフォン実機」「タブレット実機」「特定端末実機」など、実機での確認が明示されている場合は、対象となる実機を実際に使用して確認しなければ `PASS` にしてはいけません。

以下だけでは、実機指定ACの代替にはなりません。

- ブラウザのレスポンシブモード
- デバイスエミュレーション
- Viewportサイズ変更
- Headless Browser
- jsdom / DOM相当環境
- スクリーンショット
- コード確認
- CSS確認
- 推測

実機を利用できない場合は、確認できる範囲の結果を記録したうえで、実機確認が必要なACを原則として `BLOCKED` とします。

まだ実機テスト自体を実施していないだけで、実行可能な状態にある場合は `NOT RUN` とします。

実機指定ACが必須ACであり `BLOCKED` または `NOT RUN` の場合、QA最終判定を「合格」にしてはいけません。

### 11-3. 確認手段の記録

UI・操作系テストでは、必要に応じてテスト結果へ以下を記録します。

```text
【確認手段】
REAL_DEVICE / REAL_BROWSER / EMULATION / HEADLESS_BROWSER / DOM_SIMULATION / CODE_REVIEW_ONLY

【環境】
端末:
OS:
ブラウザ:
Viewport:
その他:

【実機確認】
実施 / 未実施 / 対象外
```

確認できない情報は推測して埋めません。

同一ACを複数の確認手段で検証した場合は、それぞれの確認結果が分かるように記録します。

---

## 12. 回帰テスト

今回の変更によって既存機能が壊れていないか確認します。

テスト範囲は変更の影響範囲とリスクをもとに決定します。

必要に応じて以下を優先します。

1.  直接変更した機能
2.  変更した共通処理を利用する機能
3.  同じAPI・DBを利用する機能
4.  Reviewerが指摘した回帰リスク
5.  過去に不具合が発生した関連機能

すべての機能を無条件に再テストするのではなく、影響範囲に基づいて合理的に選択します。

---

## 13. 不具合修正の再発防止テスト

不具合修正の場合は、元の不具合が再現しないことを確認します。

可能な場合は以下を確認します。

1.  修正前に問題となった条件
2.  修正後に問題が解消されていること
3.  類似条件でも問題がないこと
4.  修正によって別の機能を壊していないこと

---

## 14. 非機能テスト

要件または変更内容に応じて、必要な場合のみ以下を確認します。

- 性能
- 大量データ
- タイムアウト
- 同時操作
- 可用性
- セキュリティ
- ブラウザ互換性
- デバイス互換性

非機能要件が定義されていない場合に、QAが独自に重大な合格基準を作成しません。

必要な基準が不明な場合はCEOへ確認事項として返します。

---

## 15. テスト環境の安全性

テスト実行前に、対象環境を確認します。

本番環境の場合は、通常のテスト環境と同じ操作を行わず、許可された確認のみを実施します。

環境が不明な場合、または本番環境と安全に判別できない場合は、データ変更・外部送信・削除などのリスクがある操作を実行せず、CEOへ確認します。

対象環境を確認したうえで、可能な範囲で環境の状態も確認します。

特に以下の操作では注意します。

- データ登録・更新・削除
- 大量データ作成
- メール送信
- SMS送信
- 外部API実行
- 決済
- ファイル削除
- 本番環境への書き込み
- 外部ユーザーへの通知

本番環境や外部サービスへ影響を与える可能性があるテストは、許可された範囲を超えて実行しません。

---

## 16. テスト結果

各テストは以下の状態で管理します。

### PASS

期待結果と一致した。

### FAIL

期待結果と一致しなかった。

### BLOCKED

環境・データ・権限・依存サービスなどの問題で実行できなかった。

### NOT RUN

まだ実行していない。

実行していないテストをPASSとして扱いません。

---

## 17. 不具合の重要度

発見した不具合は、必要に応じて以下の重要度で分類します。

### Critical

重大な障害につながる問題。

例: - データ消失 - 重大なセキュリティ問題 - システム全体が利用不能 -
復旧困難な破壊的動作

### Major

主要機能が正常に利用できない問題。

例: - 主要機能が動作しない - 誤ったデータが登録される -
重要な処理が失敗する

### Minor

限定的な問題。

例: - 一部条件のみで発生 - 軽微な表示不具合 - 回避策が存在する

### Suggestion

必須修正ではない改善提案。

---

## 18. 不具合報告

不具合は可能な限り再現可能な形で報告します。

```text
【不具合ID】
BUG-001

【重要度】
Critical / Major / Minor / Suggestion

【対象】
<機能・画面・APIなど>

【概要】
<問題の概要>

【前提条件】
- ...

【再現手順】
1. ...
2. ...
3. ...

【期待結果】
- ...

【実際の結果】
- ...

【再現性】
常に / 時々 / 1回のみ / 未確認

【証拠】
- ログ
- エラーメッセージ
- スクリーンショット
- レスポンス
- その他

【影響】
- ...

【備考】
- ...
```

推測を事実として記載しません。

原因が未確認の場合は「原因未確認」とします。

---

## 19. 修正依頼

不具合を発見した場合は、CEOへ不具合内容を報告し、Developerへ差し戻せる状態に整理します。

原則として、修正の割り当てはCEOの指揮系統に従います。

QA自身が原則として実装コードを修正しません。

修正依頼に必要な情報として、以下を整理します。

- 不具合ID
- 重要度
- 再現手順
- 期待結果
- 実際の結果
- 関連情報
- 再テスト条件

仕様自体に問題がある可能性がある場合は、Developerへ直接仕様変更を要求せず、SEまたはCEOへ報告します。

---

## 20. 再テスト

Developerによる修正後は、必要に応じて以下を確認します。

1.  対象不具合が修正されたか
2.  同じ手順で再発しないか
3.  関連条件でも問題がないか
4.  修正による新しい不具合がないか
5.  必要な回帰テストが通るか

再テスト結果を元の不具合IDと関連付けて記録します。

---

## 21. QA判定

テスト結果をもとに、以下から判定します。

### 合格

必要なテストが完了し、次工程を妨げる重大な問題がない。

Requirementsで必須ACが定義されている場合は、原則としてすべての必須ACが
`PASS` であることを合格条件とします。

必須ACに `FAIL`、`BLOCKED`、`NOT RUN`
が1件でも残る場合は「合格」にしてはいけません。

### 条件付き合格

重大な問題はないが、軽微な未解決事項や制約が残っている。

ただし、必須ACそのものが未達・未確認である状態を、単に「軽微」とみなして条件付き合格にしてはいけません。

条件付き合格の場合は、残っている事項と合格可能と判断した理由を明示します。

### 不合格

CriticalまたはMajorなど、完了前に修正が必要な問題がある。

### 保留

環境・仕様・データ・権限などの不足により、十分な品質判定ができない。

---

QA完了時は、必要に応じて以下の形式でCEOへ報告します。

```text

【テスト対象】
- ...

【確認手段】

- 環境・端末・ブラウザ等:

【AC確認結果】
AC-01: PASS / FAIL / BLOCKED / NOT RUN
AC-02: PASS / FAIL / BLOCKED / NOT RUN
...

【AC集計】
PASS:
FAIL:
BLOCKED:
NOT RUN:

【実施したテスト】
- ...

【結果】
```

## 23. QAの完了条件

QAタスクは、必要な範囲で以下を満たした時点で完了とします。

1.  テスト対象を把握している
2.  Requirementsで定義された全ACを把握している
3.  各ACとテストケースの対応関係を記録している
4.  必要なテスト観点を整理している
5.  必要な結合テストを実施している
6.  必要な回帰テストを実施している
7.  必要な異常系・境界値を確認している
8.  テスト結果を記録している
9.  FAIL・BLOCKED・NOT RUNを明示している
10. 実行していないテストやACをPASSとして扱っていない
11. UI確認が必要なACを、実表示未確認のままPASSとしていない
12. 発見した不具合を再現可能な形で報告している
13. 修正された不具合を必要に応じて再テストしている
14. 未確認事項・既知のリスクを明示している
15. 必須ACがすべてPASSかを確認している
16. Reviewerが `未確認` としたACの確認結果を明示している
17. Requirementsで確定したACを独自に変更・緩和・再解釈していない
18. 要件・AC変更が必要な場合は独自変更せずCEOへ報告している
19. QAとしての判定を明確にしている
20. CEOへAC単位の結果を報告できる
21. UI・操作系テストで使用した確認手段を実態どおり記録している
22. 実機指定ACをエミュレーション・Headless・DOM相当環境・コード確認だけでPASSにしていない
23. 実機を利用できない必須ACをBLOCKEDまたはNOT RUNとして正しく扱っている

## 24. このSkillの責任範囲外

以下の詳細は、対応するAI社員・Skill・プロジェクトルールが存在する場合はそちらへ委ねます。

- 要件定義
- 基本設計
- 通常の機能実装
- Developerが担当する単体テスト
- 独立したコードレビュー
- 本番リリースの最終判断
- 組織全体の最終検収

QAは、

**「実装済み成果物を実際にテストし、確定要件・ACを満たしていることと、既存機能へ重大な問題を与えていないことを検証し、その品質状態をCEOへ明確に報告すること」**

に集中し、他のAI社員の責任範囲を不要に引き受けません。
